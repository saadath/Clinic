# معماری AI Provider Manager و پردازش اسناد

## تفکیک مسئولیت‌ها

```text
درخواست کاربر مجاز
  → انتخاب حداقل داده و کنترل دسترسی
  → حل تنظیمات Task / پزشک / فیلد
  → انتخاب نسخه Prompt و مدل دارای قابلیت
  → ثبت درخواست و ارسال به Queue پس از commit
  → Adapter خارجی یا محلی
  → اعتبارسنجی خروجی و منشأ
  → ذخیره پیشنهاد
  → بازبینی کاربر مجاز
  → ثبت مقدار با تاریخچه
```

هسته به قرارداد `AIProvider` وابسته است؛ هر Adapter عملیات healthCheck، capabilities و execute را ارائه می‌کند. DTO درخواست شامل task، model، ورودی انتخاب‌شده، schema خروجی، timeout و correlation ID است. DTO پاسخ شامل نتیجه، مصرف، finish reason، metadata منبع و وضعیت است. قابلیت‌هایی مانند text، structured_output، vision، transcription و embeddings صریح‌اند؛ صرف سازگاری نام API، تضمین تمام قابلیت‌ها نیست.

Adapterهای اولیه عبارت‌اند از OpenAICompatibleAdapter، AnthropicMessagesAdapter و قرارداد CustomProvider. Ollama از مسیر سازگار یا Adapter مستقل پس از آزمون استفاده می‌کند. تفاوت مسیر API، header، پیام، فایل و usage در Adapter محصور است. مدل بدون transcription نمی‌تواند Task صوت را اجرا کند. OCR قرارداد مستقل دارد و الزاماً نیازمند LLM نیست.

## تنظیم و انتخاب مدل

ترتیب حل تنظیمات: سیاست و ممنوعیت سراسری → فعال‌بودن ماژول/Task → مجوز پزشک → تنظیم مجاز فیلد → انتخاب مدل و prompt. هیچ تنظیم محلی ممنوعیت سراسری یا بازبینی پزشکی را لغو نمی‌کند. تعارض یا capability ناکافی به خطای روشن می‌انجامد.

مدیر Provider، URL، کلید رمزنگاری‌شده، timeout و مدل‌ها را تنظیم می‌کند. تست اتصال بدون داده بیمار انجام می‌شود. برای جلوگیری از SSRF، URL صرفاً توسط مدیر مجاز و بر مبنای allowlist میزبان و پورت ثبت می‌شود؛ دسترسی به سرویس محلی AI به‌شکل صریح مجاز می‌شود و آدرس metadata یا شبکه ناخواسته مسدود است. TLS برای سرویس بیرونی اجباری است.

Taskها: speech_to_text، clinical_note، medical_structuring، ocr، lab_extraction، history_summary، clinical_support و document_generation. Taskهای مدیریتی، وبلاگ و مکاتبه نیز با همان قرارداد و مجوز جدا افزوده می‌شوند. برای هر Task مدل اصلی، fallback سازگار، سقف درخواست، timeout و schema تعیین می‌شود. fallback به Provider خارجی باید مطابق سیاست انتقال داده باشد و خاموش‌بودن سرویس مجوز ارسال به مقصد دیگری نیست.

## Prompt و خروجی

PromptTemplate دارای نسخه منتشرشده غیرقابل ویرایش است. scope سراسری، پزشک، ماژول و فیلد مشخص است. در هر درخواست نسخه دقیق نگهداری می‌شود. آزمایش Prompt با داده ساختگی انجام می‌شود.

دستورهای ثابت استخراج پزشکی: چیزی خارج از منبع اضافه نشود، موارد نامشخص مشخص بمانند، متن واقعی از استنباط تفکیک شود و ادعای استخراج تا حد امکان evidence داشته باشد. خروجی ساختاریافته با JSON Schema اعتبارسنجی می‌شود؛ نوع اشتباه، واحد نامعلوم و فیلد غیرمجاز به‌طور خودکار در پرونده نوشته نمی‌شوند. confidence ارائه‌شده توسط مدل تضمین صحت نیست.

متن بیمار، PDF و OCR ورودی غیرقابل اعتمادند. دستورهای داخل آن‌ها مجوز تغییر سیاست یا دسترسی به ابزار نمی‌دهند. LLM دسترسی مستقیم به دیتابیس، SQL، shell یا کلیدهای برنامه ندارد. خروجی HTML/Markdown پیش از نمایش sanitize می‌شود.

## پردازش غیرهم‌زمان و خطا

وضعیت درخواست: queued → running → succeeded/failed/cancelled؛ پیشنهاد موفق pending می‌ماند تا accepted/rejected/stale شود. تلاش‌های retry جدا ثبت می‌شوند. retry برای خطای موقت شبکه، 429 و برخی 5xx با backoff محدود انجام می‌شود؛ خطای schema، authentication و مجوز بی‌دلیل تکرار نمی‌شود. idempotency مانع اعمال دوباره نتیجه و duplication داخلی می‌شود؛ هزینه احتمالی تکرار سرویس خارجی صریح ثبت می‌شود.

job پیش از خواندن اطلاعات و هنگام اعمال نتیجه مجوز و وضعیت پرونده را دوباره بررسی می‌کند. قطع سرویس AI نباید بیمار، فرم، پرونده و نوبت دستی را از کار بیندازد. job قدیمی یا متعلق به فرم تغییرکرده نتیجه را بی‌صدا اعمال نمی‌کند. UI وضعیت و امکان بررسی خطا را نمایش می‌دهد.

## محرمانگی و بازبینی

فقط منابع انتخاب‌شده و مجاز ارسال می‌شوند. کد ملی، موبایل و نام در صورت عدم نیاز حذف یا با شناسه مستعار جایگزین می‌شوند؛ حذف خودکار همه شناسه‌ها از متن آزاد تضمین‌پذیر نیست و باید پیش‌نمایش داده ارسالی و سیاست کلینیک وجود داشته باشد. Provider محلی و خارجی برچسب روشن دارند. payload و secret در لاگ عمومی یا ابزار پایش قرار نمی‌گیرند.

پیشنهاد حاوی مقدار، منبع، صفحه یا قطعه متن، نسخه فرم و revision مقصد است. کاربر مجاز می‌تواند قبول، اصلاح یا رد کند. قبول پیشنهاد با ویرایش مقدار، ثبت revision، ثبت provenance و review event در یک تراکنش انجام می‌شود. تأیید دستیار جای تأیید نهایی پزشک را نمی‌گیرد. ابزار کمک بالینی پیشنهاد ارائه می‌کند و تشخیص یا نسخه را خودکار نهایی نمی‌کند.

## OCR، صوت و PDF

- فایل اصلی immutable در storage خصوصی نگهداری می‌شود؛ checksum، MIME و ثبت‌کننده مشخص‌اند.
- PDF دارای لایه متن ابتدا با ابزار استخراج متن پردازش می‌شود؛ PDF اسکن‌شده با renderer محدود به تصویر صفحه و سپس OCR تبدیل می‌شود.
- OCR محلی پیشنهادی Tesseract با زبان‌های fas و eng است؛ Poppler برای متن و صفحه PDF بررسی می‌شود. این‌ها در مرحله هشتم و پس از بررسی مجوز و توزیع نصب می‌شوند.
- هر صفحه وضعیت مستقل دارد؛ retry یک صفحه نباید کل سند یا پیشنهادها را تکرار کند. متن خام، متن اصلاح‌شده و تفسیر در فیلدهای جدا ذخیره می‌شوند.
- صوت با اجازه کاربر ضبط و فایل اصلی نگهداری می‌شود. STT ابتدا transcript تولید می‌کند؛ استخراج فیلد از transcript یک Task جدا با منشأ مشخص است.
- FFmpeg در صورت نیاز به تبدیل صوت/ویدئو و Chromium برای PDF فارسی در مراحل مربوط اضافه می‌شوند. محدودیت صفحات، مدت، حافظه و زمان از قبل تعیین می‌شود.

## آزمون و مشاهده‌پذیری

FakeProvider قطعی برای توسعه و تست، fixture پاسخ معتبر/نامعتبر، timeout، rate limit، مدل فاقد قابلیت، fallback، داده غیرمجاز و prompt injection استفاده می‌شود. تست واقعی فقط با کلید تنظیم‌شده و داده ساختگی اجرا خواهد شد. هیچ ادعای اتصال موفق بدون اجرای تست سرویس واقعی ثبت نمی‌شود. داشبورد مصرف، تعداد تلاش، latency، هزینه تخمینی و وضعیت تأیید را بدون نمایش عمومی محتوای پزشکی نشان می‌دهد.
