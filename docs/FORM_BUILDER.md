# معماری فرم‌ساز پویا

> تطبیق پیاده‌سازی مرحله چهارم: بخش‌ها و فیلدها در `form_versions.schema_json` نگه‌داری می‌شوند؛ drag/drop بومی جایگزین SortableJS شده است. نمونه‌ها به بیمار متصل نیستند و مقادیرشان متن JSON است تا ترتیب ردیف‌ها در MySQL حفظ شود. جزئیات و قابلیت‌های هنوز آماده‌نشده در [مرحله چهارم](PHASE_4.md) ثبت شده‌اند؛ موارد آینده این سند به معنی پیاده‌سازی فعلی نیستند.

## مدل و چرخه عمر

هر پزشک چند FormTemplate دارد. هر قالب دارای نسخه‌های draft و published است. انتشار، schema را اعتبارسنجی و در یک تراکنش snapshot و hash تولید می‌کند. نسخه منتشرشده و تمام فیلدها و بخش‌های آن دیگر قابل ویرایش نیستند؛ ویرایش یک draft جدید از نسخه پیشین می‌سازد. مراجعه همیشه به `form_version_id` مشخص وصل است. غیرفعال‌کردن قالب انتخاب آن برای مراجعه جدید را متوقف می‌کند و مانع مشاهده سابقه نمی‌شود.

کپی یا اشتراک قالب فقط تعریف فرم را منتقل می‌کند. اطلاعات بیمار، کلید API و تنظیمات محرمانه پزشک کپی نمی‌شوند. کپی مالک و شناسه مستقل دارد. قالب پیش‌فرض برای هر پزشک و کاربرد در `doctor_form_defaults` تعیین می‌شود.

## قرارداد تعریف فیلد

هر فیلد یک `field_key` پایدار، نوع، عنوان ترجمه‌شده، بخش، ترتیب، عرض ستون، توضیح، مقدار پیش‌فرض، وضعیت فعال، قوانین اعتبارسنجی، گزینه‌ها، واحد، شرط نمایش، محدودیت محرمانگی، مجوز دستیار/منشی، تنظیم خروجی و AI دارد. تغییر معنای یک فیلد نیازمند کلید جدید است؛ تغییر صرف عنوان با نسخه جدید همان کلید را نگه می‌دارد.

فهرست نوع‌ها با FieldTypeRegistry توسعه می‌یابد. هر نوع باید قراردادهای schema، renderer، validator، serializer و export formatter داشته باشد؛ افزودن نوع جدید به تغییر یک switch بزرگ در چند بخش نیاز ندارد.

| گروه | نوع‌ها |
|---|---|
| متن | short_text، long_text، rich_text، email، phone، url |
| عدد | integer، decimal، number_range، slider، medical_unit |
| زمان | date، datetime، time |
| انتخاب | checkbox، radio، select، multi_select، color |
| فایل | file، image، multiple_images، pdf، audio، video، signature |
| ساختار | repeater، heading، description، divider، hidden |
| محاسبه | calculated |

Rich text سمت سرور sanitize می‌شود. فیلد hidden مخزن secret نیست و نباید دسترسی پنهان ایجاد کند. امضا یک پیوست دارای ثبت‌کننده و زمان است؛ به‌خودی‌خود امضای دیجیتال حقوقی محسوب نمی‌شود.

## شرط و محاسبه

شرط‌ها AST محدود با عملگرهای allowlist مانند equals، in، exists، gt و and/or هستند. اجرای JavaScript، PHP، SQL یا `eval` از تعریف پزشک مجاز نیست. قبل از انتشار، ارجاع به فیلد ناموجود، دور وابستگی، ناسازگاری نوع و عمق/تعداد بیش از حد رد می‌شود.

محاسبات از parser محدود با متغیرهای مشخص و عملگرهای حسابی مجاز استفاده می‌کنند. BMI فقط با واحد استاندارد و مقدار معتبر محاسبه می‌شود؛ تقسیم بر صفر، مقدار ناموجود و تبدیل واحد ناسازگار خروجی خطای قابل فهم می‌دهد. نتیجه در سرور دوباره محاسبه می‌شود. محاسبه از داده مخفی از کاربر نباید موجب افشای غیرمستقیم شود.

فیلد شرطاً پنهان، در حالت draft مقدار قبلی را حفظ می‌کند اما در حالت نامرتبط برای validation اجباری و export استفاده نمی‌شود؛ مقدار ارسالی تازه برای فیلدی که کاربر حق ویرایش آن را ندارد رد می‌شود. در انتشار schema، سیاست visibility و export به‌صورت صریح ثبت خواهد شد. پاک‌کردن داده قبلی نیازمند عمل صریح و تاریخچه است.

## تکرارشونده‌ها و فایل

هر ردیف repeater شناسه پایدار مستقل از ترتیب ظاهری دارد؛ reorder نباید مقادیر را به ردیف دیگر منتقل کند. مسیر item_path از شناسه ردیف‌ها ساخته می‌شود. عمق، تعداد ردیف و حجم payload محدود است. مقادیر پزشکی در value_json دارای type و واحد روشن نگهداری می‌شوند؛ امکان افزودن projection عددی برای گزارش‌های پرتکرار پس از شناسایی نیاز وجود دارد.

آپلود در سرویس Files انجام می‌شود. فرم فقط شناسه فایل مجاز را ارجاع می‌دهد؛ فایل بیمار دیگر یا URL خارجی دلخواه پذیرفته نمی‌شود. renderer سابقه نسخه قدیمی را می‌فهمد و نوع استفاده‌شده در سوابق حذف فیزیکی نمی‌شود.

## تعامل کاربر و سرور

رابط طراحی شامل فهرست نوع فیلدها، بوم بخش‌ها، پنل تنظیمات و پیش‌نمایش است. جابه‌جایی با SortableJS و جایگزین دکمه‌های جابه‌جایی برای دسترس‌پذیری انجام می‌شود. ذخیره draft دارای revision/optimistic lock است تا ویرایش هم‌زمان یک پزشک داده را بازنویسی نکند. پیش‌نمایش همان renderer مورد استفاده در پرونده را به‌کار می‌برد.

Backend در هر ذخیره، نوع، نسخه فرم، دسترسی، schema، وابستگی شرط و فایل را بررسی می‌کند. schema دریافتی مرورگر معتبر فرض نمی‌شود. پاسخ API فقط فیلدهایی را برمی‌گرداند که کاربر اجازه مشاهده دارد؛ فیلد محرمانه در HTML یا JSON منشی قرار نمی‌گیرد.

## اتصال AI

`ai_config` شامل enabled، روش‌های ورودی، task، مدل مجاز اختیاری، prompt_version، output schema و الزام بازبینی است. تنظیم فیلد تنها در محدوده قابلیت و مجوز سراسری و پزشک معتبر است. هیچ تنظیمی نمی‌تواند الزام بازبینی اطلاعات بالینی را دور بزند. انتخاب model صرفاً شناسه تنظیمات سرور است و حاوی API key نیست.

درخواست AI با نسخه فرم، شناسه فیلد، revision فعلی و منابع انتخاب‌شده ثبت می‌شود. پیشنهاد جدا نمایش داده می‌شود؛ قبول، اصلاح و رد آن هرکدام رویداد ثبت می‌کنند. اگر مقدار فیلد بعد از شروع درخواست تغییر کرده باشد، پیشنهاد stale است و نباید بی‌صدا روی مقدار جدید اعمال شود.

## معیارهای آزمون

- فرم داخلی با شرح حال، آلرژی، معاینه، داروی تکرارشونده و BMI و فرم چشم با VA، IOP و معاینه مستقل ساخته شوند.
- انتشار نسخه دوم فرم داخلی روی مقدار و خروجی مراجعه نسخه اول اثری نگذارد.
- condition نامعتبر، ارجاع دوری، محاسبه غیرمجاز و payload نامتناسب در سرور رد شوند.
- دستیار نتواند فیلد ممنوع را با درخواست مستقیم ویرایش یا نسخه نهایی را تأیید کند؛ منشی داده محرمانه دریافت نکند.
- جابه‌جایی repeater، بازخوانی مقادیر، کپی قالب، پیش‌نمایش و export ترتیب و هویت داده را حفظ کنند.
- پیشنهاد AI کهنه، فایل متعلق به بیمار دیگر و ویرایش هم‌زمان به شکل صریح مدیریت شوند.
